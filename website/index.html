The wedge

Dependency checkmarks, for agent artifacts.

Each scheduled job declares its inputs and outputs. When it finishes, Almanac records a manifest — content hash, schema version, commit SHA. When a downstream job is about to run, it checks: does a materialized manifest exist for each of my inputs?

✅

Ready

A fresh manifest exists and its version matches the consumer's minimum.

STATUS:CONFIRMED
❌

Missing

No manifest within the freshness window. The job refuses to start.

STATUS:CANCELLED
⚠️

Version mismatch

A manifest exists but its schema version is older than required.

skipped:version_mismatch

This is data lineage — the thing Palantir Foundry and Dagster do for data pipelines — applied to agent artifacts. Encoded as RELATED-TO;RELTYPE=DEPENDS-ON (RFC 9253) so the relationship survives every calendar sync, with state mirrored into STATUS + emoji SUMMARY so every client renders it.

How it works

One URL. Standard protocols. No install.

Any calendar client
Google · Apple · Outlook · DAVx⁵ · Thunderbird
Subscribes to one URL. Just renders events.
↑ subscribes (one-way ICS feed)
Almanac Rust
Reads events · renders RFC 5545/7986/9253 · encodes lineage
/calendar/<community>.ics · /runs.ics · /schedule.ics
↑ reads events
Event source
Buzz relay, or any Nostr event producer
The source of truth. Almanac is a derived view.

Quick start

Running in under a minute.

run the server
$ cargo build --release
$ ./target/release/almanac-server
→ almanac server listening on 0.0.0.0:8787
→ seeded demo community `demo`
$ curl localhost:8787/calendar/demo.ics | head
BEGIN:VCALENDAR
BEGIN:VEVENT
SUMMARY:✅ Daily research brief
STATUS:CONFIRMED
RRULE:FREQ=DAILY;BYHOUR=9
the CLI
$ almanac subscribe --community research
http://localhost:8787/calendar/research.ics

$ almanac check weekly-strategy
Lineage for `weekly-strategy`:
  ✅ ready (v3)  research-brief
    ← produced by `daily-brief`

$ almanac declare --schedule weekly \
    --role consume --schema research-brief

Then paste the URL into any calendar app. Done.

Honest limits

Calendar latency is real. We won't pretend otherwise.

ICS feeds are poll-based, and clients poll on their schedule, not yours. This is a property of calendar clients, not Almanac.

ClientTypical pollWorst seen
Google Calendar12–24 hup to ~5 days
Apple Calendar (iCloud)~1 ha few hours
Outlook.com~3 h~1 day
DAVx⁵ → local CalDAVminutesminutes
Thunderbirdminutesminutes

For near-real-time, use the CalDAV path (Phase 2) or point a DAVx⁵-style client at a local CalDAV server. The ICS feed is the universal baseline — not the low-latency option.
